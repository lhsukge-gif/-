# 기존 작품을 포함한 배포

## 필요한 호스팅
Python 3 실행, 항상 실행되는 단일 서버 프로세스, 영구 디스크, HTTPS 및 SSE 스트리밍을 지원해야 합니다. 서버 여러 개로 복제하지 마세요. GitHub Pages나 요청마다 종료되는 함수만으로는 실행할 수 없습니다.

## 데이터 포함 배포 파일
`/workspace/gallery-deployment.tar.gz`에 서버, 화면, 배포 설정, 현재 SQLite 백업을 포함했습니다. 이 백업에는 학생 작품과 댓글이 있으므로 서버 내부로 전송하고 공개 파일 다운로드 경로에 두지 마세요. 앱은 데이터 파일 URL을 제공하지 않습니다. Git에는 데이터베이스를 추가하지 않습니다.

1. 서버에 압축 파일을 전송하고 `/opt/gallery`에 압축 해제합니다.
2. `/var/lib/gallery`를 영구 볼륨에 연결합니다. 코드 교체나 재배포 때 이 디렉터리를 삭제하지 않습니다.
3. Python 3와 실행 사용자 `gallery`를 준비하고, 코드와 백업은 해당 사용자에게 읽기 권한을, 영구 디렉터리에는 쓰기 권한을 줍니다.
4. 다음 환경변수로 실행합니다.

```sh
cd /opt/gallery
GALLERY_DATA_DIR=/var/lib/gallery \
GALLERY_SEED_DB=/opt/gallery/backup/gallery.db \
PORT=8080 sh deploy/start.sh
```

처음 실행할 때만 백업을 복원합니다. 이미 `gallery.db`가 있으면 무결성을 확인하고 그대로 사용합니다. 기존 데이터가 손상되었으면 오류로 중단하며 빈 DB로 대체하지 않습니다. 서버 실행 전에 초기화하세요. 운영 중 DB를 덮어쓰지 마세요.

## 프로세스·HTTPS·실시간 연결
Linux systemd 서버에서는 `gallery.service`를 `/etc/systemd/system/`에 설치하고 `systemctl daemon-reload`, `systemctl enable --now gallery`로 관리할 수 있습니다. 서비스 사용자와 디렉터리 준비가 선행되어야 합니다. 관리형 호스팅에서는 위 실행 명령과 환경변수를 설정하고 인스턴스를 1개로 유지합니다.

호스팅에서 발급한 도메인과 HTTPS를 연결합니다. nginx를 사용한다면 기존 HTTPS server 블록에 `nginx-location.conf`의 location을 적용하고 `nginx -t` 검증 후 재로드합니다. 8080은 외부 접근을 막고 HTTPS 프록시로만 전달합니다. SSE 버퍼링·캐시를 끄고 읽기 제한을 75초 이상으로 지정합니다. 앱은 20초마다 이벤트를 보내 연결을 유지합니다.

## 배포 후 최종 확인
- 실제 HTTPS 주소에서 기존 작품 4개, 포스터 4개, 댓글 12개, 반응 14개를 확인합니다(추가 사용 전 백업 기준).
- 서로 다른 기기에서 접속해 한 기기의 작품 등록, 댓글, 좋아요가 다른 기기에 새로고침 없이 나타나는지 확인합니다.
- 서버를 재시작하고 코드만 재배포한 뒤 새 작품과 댓글이 남아 있는지 확인합니다.
- 영구 볼륨의 DB를 SQLite backup API로 주기적으로 별도 저장소에 백업합니다. 재배포와 디스크 장애는 다르므로 영구 볼륨만으로 백업을 대체하지 않습니다.

현재 환경에서 초기 데이터 이전, 서버 구동, SSE 알림, 데이터 수정, 프로세스 재시작, 코드 디렉터리 교체 및 기존 DB 보존을 검증했습니다. 실제 호스팅의 볼륨·HTTPS·nginx/systemd 적용은 아직 실행하지 않았습니다.
